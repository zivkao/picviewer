# Pic Viewer

<img src="assets/picviewer.png" width="96" align="right" alt="">

A desktop image viewer that opens most of what a camera or a phone produces.

## Setup

```
py -3.13 -m venv .venv
.venv\Scripts\python.exe -m pip install -r requirements.txt
```

## Run

```
.venv\Scripts\python.exe -m picviewer            # empty, then Ctrl+O or drop a file
.venv\Scripts\python.exe -m picviewer photo.cr2  # opens the file, folder becomes the playlist
.venv\Scripts\python.exe -m picviewer D:\Photos  # opens a folder
```

Or double-click `run.bat`, which works from any folder and takes the same
arguments. The `-m picviewer` form above only works from the project folder,
because `-m` puts the *current* directory on `sys.path` and nothing else;
`run.bat` sets `PYTHONPATH` instead of changing directory, so a relative path
argument still resolves against where you ran it.

## Keys

| | |
|---|---|
| `Ctrl+O` | open |
| `←` `→` `Space` `PgUp` `PgDn` | previous / next |
| `Home` `End` | first / last |
| wheel, `+` `-` | zoom at the cursor |
| `0` / `1` / double-click | fit / actual size / toggle |
| drag | pan |
| `F11` | fullscreen |
| `Del` | move to Recycle Bin |
| `Esc` `Ctrl+Q` | leave fullscreen / quit |

Dropping works too: one file opens it with its folder as the playlist, several
files become the playlist themselves, and a folder opens everything in it.

Everything is also on the menu bar (File / Go / View / Help) and the toolbar, so
nothing is keyboard-only. Buttons grey out when they cannot act. `Ctrl+E` reveals
the current file in Explorer, `Ctrl+C` copies the image to the clipboard.

## Icon

`picviewer/icon.ico`, generated by `assets/make_icon.py` -- an aperture, drawn
rather than drawn from a set, at seven sizes from 16 to 256 px. Regenerate with:

```
.venv\Scripts\python.exe assets\make_icon.py
```

The window icon alone is not enough on Windows: the taskbar groups by
AppUserModelID and takes its icon from whoever owns it, so a Python app that
does not claim one shows the interpreter's logo. `__main__.py` claims
`zivkao.picviewer` before the first window exists.

## Logs

`%LOCALAPPDATA%\PicViewer\logs\picviewer.log` (Help -> Open Log Folder), rotating
at 1 MB with 3 backups. Every open, decode, failure and crash lands there,
including which decoder handled each file:

```
INFO  picviewer.loader  decoded synthetic.dng via raw in 95ms -> 800x600 (1.4 MB)
INFO  picviewer.window  copied actually_png.jpg to clipboard
```

The file handler is not optional comfort: the app runs under `pythonw.exe`, which
has no console, so stderr goes nowhere and an unlogged failure leaves no trace at
all.

Every run opens with the environment, because decode bugs are routinely specific
to a library version and a report without it cannot be reproduced:

```
--- Pic Viewer 0.1.0 starting, pid 429480 ---
os      : Windows-11-10.0.26300-SP0 AMD64      pyside6 : 6.11.2
python  : 3.13.13                              pil     : 12.3.0
screen  : BenQ GW2381 1920x1200 @ 96 dpi, ratio 1.00
```

A failure says what the file was, what it was taken for, and what each decoder
made of it:

```
dispatch broken.jpg: 4096 bytes, sniffed jpeg, candidates qt(100)
decode failed for broken.jpg (4096 bytes, jpeg): Could not decode broken.jpg
    qt: Unsupported image format
```

`-v` adds the dispatch detail and is what a bug report should carry. It applies
only to this application's own loggers -- Pillow at debug level logs a line per
plugin it imports, and a debug log nobody can read is worth no more than none.

## Installing

```
.venv\Scripts\python.exe -m pip install pyinstaller
.venv\Scripts\python.exe -m PyInstaller packaging/picviewer.spec --noconfirm
powershell -ExecutionPolicy Bypass -File packaging\install.ps1 -DesktopShortcut
```

Installs per-user into `%LOCALAPPDATA%\Programs\PicViewer`: no administrator
prompt, a Start Menu shortcut, an entry under Settings > Apps, and registration
under "Open with" for 24 formats. Remove it from Settings > Apps, or with
`install.ps1 -Uninstall`, which leaves nothing behind but the log folder.

Windows will not let an installer claim a file type as the *default* handler --
that is deliberate, to stop programs fighting over associations. Right-click an
image, Open with, Choose another app, tick Always.

The build is one folder, 177 MB, not one file: a `--onefile` build unpacks
itself to a temp directory on every launch, which is seconds of delay each time
you double-click an image. PyInstaller is pointed at `packaging/launcher.py`
rather than `picviewer/__main__.py`, because it runs its target as a top-level
script and the relative imports in `__main__.py` need a real package.

## Tests

```
.venv\Scripts\python.exe tests\run_all.py        both layers
.venv\Scripts\python.exe tests\run_all.py -u     unit only, about a second
```

**`tests/unit/`** -- 148 pytest cases over the pure logic: container sniffing,
decoder ranking, cache eviction and its failure memory, playlist ordering, the
colour helpers. Real assertions, no files, no display, under a second.

Every bug found while building this lives here as a regression case. The worst
one was in decoder ranking -- pure logic that a unit test catches instantly,
found originally only by hand-building a DNG. Reintroducing each of those six
defects turns the suite red, which is the only evidence that a green suite is
worth anything.

**`tests/functional/`** -- nine end-to-end suites that decode real files, build a
real window, and send real drag and key events, all offscreen
(`QT_QPA_PLATFORM=offscreen`). They generate their own fixtures into
`.testwork/`: samples in every writable format, a hand-built DNG so the RAW path
runs without a camera, and deny-read files reproducing an unreadable-file
failure.

These report by printing rather than asserting, because what they establish is
mostly better read than asserted -- which decoder won, how long a decode took,
what the status bar ended up saying. `run_all.py` judges them on exit code and
failure markers, which is weaker than an assertion; treat them as instrumented
walkthroughs, and put anything that can be pinned down exactly in `tests/unit/`.

## How it works

**Dispatch** (`sniff.py`, `decoders/registry.py`) — files are identified by magic
bytes first and extension second, because extensions lie. Each decoder scores its
own confidence and the registry tries them highest-first, falling through on
failure.

The awkward case is TIFF: every TIFF-based RAW (NEF, ARW, CR2, DNG) has TIFF magic
bytes, and Pillow will decode such a file *successfully* — returning the small
embedded preview from IFD0 rather than the photo. Falling through on exceptions
does not help when nothing throws, so the extension breaks the tie: a TIFF
container not named `.tif` goes to the RAW decoder.

**Two-stage RAW** (`decoders/raw_decoder.py`) — demosaicing costs 1-3 seconds, so
the embedded JPEG preview is shown first (a few ms) and the full decode replaces
it in place, without disturbing zoom or pan.

**Drops** (`viewer.py`) — the canvas handles its own drag-and-drop rather than
leaving it to the window. A `QGraphicsView` switches on `acceptDrops` for its
viewport so it can offer drags to graphics items, and marks the event handled
whether or not anything took it — so a drop landing on the canvas, which is
where the cursor always is, never reaches the window underneath.

**Failures** (`decoders/registry.py`, `cache.py`) — readability is checked before
any decoder is tried, so an unreachable file says so instead of surfacing as
`heif: [Errno 13] Permission denied`, which blames the format for a filesystem
problem. Failures are reported on the canvas rather than in a dialog (a folder of
unreadable files would otherwise mean one modal per image) and are remembered by
cache key, so the prefetcher stops retrying them. The key carries mtime and size,
so a file that is later fixed is picked up on its own.

**Threading** (`loader.py`) — decoding runs on a `QThreadPool`; results carry a
generation number so anything the user has already navigated past is discarded.
Neighbours are prefetched at a lower priority.

**Cache** (`cache.py`) — LRU with a budget in *bytes*, not entries. A hundred
thumbnails and a hundred 100-megapixel TIFFs are the same count and three orders
of magnitude apart in memory.

**Colour** (`color.py`) — EXIF orientation is applied and embedded ICC profiles are
converted to sRGB. Without the first, phone photos are sideways; without the
second, Adobe RGB and Display P3 files look washed out.

## C++ port

`cpp/` holds a port to C++ with Qt6, LibRaw and libheif, built against an
isolated MSYS2 toolchain in `.msys64/` that is to this what `.venv` is to the
Python version. The decoder architecture is the same; 98 assertions cover it
and seven reintroduced defects all turn the suite red. See [cpp/README.md](cpp/README.md).

Both are now packaged and install side by side, into separate directories with
separate Start Menu entries, so neither disturbs the other. The C++ build is
139 MB against 177 MB and decodes faster throughout -- 9x on a small JPEG,
1.7x on a real 19 MB Canon CR2. Startup is the same in both, despite an
earlier measurement here that said otherwise; see `tools/benchmark.ps1`.

The first real camera RAW and phone HEIC either build has seen both decode
correctly -- see [cpp/README.md](cpp/README.md) for what that proved about the
decoder ranking.

## Not built yet

Thumbnail strip (the disk-backed thumbnail cache it needs is the real work),
animated GIF/WebP playback (frame 0 is shown), slideshow, EXIF detail panel,
rotate/flip, and any settings at all -- the cache budget and zoom limits are
constants in the source.

Untested rather than missing: high-DPI displays. Nothing in the code accounts
for `devicePixelRatio`, so on a scaled display "100%" almost certainly does not
mean one image pixel per screen pixel. It has only ever run at 100% scaling.
